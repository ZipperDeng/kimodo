# Training Kimodo

The original release contains inference weights but no data loader or training
entry point.  `kimodo.scripts.train` implements the recipe in section 4.3 of
the technical report while reusing the released motion representation and
two-stage denoiser.

## Set up the environment

On a new Linux machine, clone the repository and run the setup script from its
root. It installs `uv` when necessary and creates a Kimodo environment for
both training and inference, installs all dependencies, and verifies CUDA:

```bash
bash scripts/setup_env.sh
source .venv/bin/activate
```

The default environment is `.venv`. To keep it outside the workspace, provide
a user-level path:

```bash
bash scripts/setup_env.sh --venv-dir "$HOME/venvs/kimodo"
source "$HOME/venvs/kimodo/bin/activate"
```

### Optional: prepare LLM2Vec for inference and benchmarks

Training does not load a text encoder: it reads the text vectors that AssetCMS
published into the release, and `training.text_encoder` only selects the
snapshot and records provenance. The LLM2Vec model is needed only to encode new
prompts at inference time and to run the TMR benchmark (and by AssetCMS when it
encodes texts upstream). Skip this section on a training-only machine.

If the gated `meta-llama/Meta-Llama-3-8B-Instruct` base model is unavailable
from Hugging Face, download it from ModelScope and map it into the Linux Hugging
Face cache:

```bash
pip install modelscope

export HF_HOME="$HOME/.cache/huggingface"
MODEL_DIR="$HOME/models/Meta-Llama-3-8B-Instruct"
HF_MODEL_DIR="$HF_HOME/hub/models--meta-llama--Meta-Llama-3-8B-Instruct"

modelscope download \
  --model LLM-Research/Meta-Llama-3-8B-Instruct \
  --local_dir "$MODEL_DIR"

mkdir -p "$HF_MODEL_DIR/snapshots" "$HF_MODEL_DIR/refs"
ln -sfn "$MODEL_DIR" "$HF_MODEL_DIR/snapshots/modelscope"
printf '%s\n' modelscope > "$HF_MODEL_DIR/refs/main"

# Enable these after the first successful model load.
export HF_HUB_OFFLINE=1
export TRANSFORMERS_OFFLINE=1
```

## Prepare data

Kimodo trains only from an AssetCMS release. AssetCMS owns dataset conversion,
annotation, text encoding, and publishing; see its motion pipeline
documentation. Kimodo treats the release as read-only: `kimodo_train` computes
its own normalization statistics into the run's output directory. Training
never connects to the vector database or loads a frozen text encoder.

### Release layout

```text
<release>/
├── manifest.json                       # release name, selection, source datasets, checksums
├── source.json                         # fps, coordinate_system, units
├── motion-text-index.json              # vector schema and model provenance
├── samples/{train,val,test}.jsonl      # catalog for retrieval; not read by Kimodo
├── training-vectors/<encoder>/         # float16 mmap: metadata.json, keys.txt, vectors.f16
└── skeletons/<skeleton>/               # somaskel30, smplx22, ...
    ├── source.json
    ├── {train,val,test}.jsonl          # training manifests, generated by publish
    ├── motions/                        # float32 mmap motion store, packed by publish
    │   ├── index.json                  # per motion: source, frame offset, frames; checksums
    │   ├── rotations.f32               # [frames, J, 4] unit quaternions (w, x, y, z)
    │   └── roots.f32                   # [frames, 3] root positions
```

A release is self-contained: copy or move the whole directory to a training
machine; no source dataset is needed. `index.json` records the SHA-256 of
`rotations.f32` and `roots.f32` for verifying a transfer. `--dataset-root`
always points at the release directory. Kimodo rejects any directory without a
release `manifest.json`, and selects `skeletons/<skeleton>/` from the config.

Each manifest row contains `name`, a `motion_index` into the skeleton's motion
store, a `text_vector_keys` list, and optionally `start_frame` / `end_frame`
for a temporal slice; several rows can share one motion. Reading a sample is a
single mmap slice of only the selected frames, with no file opens or
decompression, and the page cache is shared across DataLoader workers and
distributed processes. Quaternions are converted back to `local_rot_mats`
(`T,J,3,3`) on load; publish rejects motions whose rotation matrices do not
survive that round trip within `1e-4`. Motions are 30 FPS. Kimodo validates
every row's index and frame range at startup and rejects releases without a
motion store (older releases referenced NPZ files); republish those.
`source.json` can declare
`skeleton`, `joint_count`, and `fps`. Training rejects metadata, joint counts,
or a release `selection.skeleton` that do not match the config.

`text_vector_keys` are SHA-256 digests of the stripped texts and index
`training-vectors/<encoder>/keys.txt`. The mmap snapshot supports multi-worker
DataLoaders and shares the operating-system page cache across workers and
distributed processes.

#### SMPL-X

SMPL-X training uses 22 body joints and `configs/train_smplx.yaml`. Publish the
release with the `smplx22` variant and use the SMPL-X config for training.
`configs/train_smplx_smoke.yaml` provides the four-step pipeline check.

### Motion statistics

There is no separate statistics step. Before the first batch step, a new run
computes feature means and standard deviations into
`<output>/stats/motion/{global_root,local_root,body}/{mean,std}.npy`, the
layout every exported checkpoint references. They use the training transform
(random `max_frames` crop and random heading) on a fixed random subset of the
training split, `training.stats.max_samples` rows (50k by default; mean and
standard deviation do not need every row). Each distributed rank featurizes
its shard on its GPU and the partial sums are all-reduced. `--resume` reuses
the run's statistics and refuses to start without them.

Root smoothing dominates feature extraction. It is batched (one block-diagonal
solve per multigrid level instead of one per clip, matching the per-clip
reference to float precision) and runs in DataLoader workers, so it overlaps
the GPU step in both statistics and training. Set `training.num_workers` to
keep up with the GPUs; it applies to both.

### Optional: BGE-M3 multilingual conditioning

Publish the release with `--encoder bge-m3`, then add
`--text-encoder bge-m3` to `kimodo_train`. BGE-M3 uses one normalized
1024-dimensional CLS embedding token and does not require a query instruction.
The preset changes `model.denoiser.llm_shape` from `[1,4096]` to `[1,1024]`;
training rejects embeddings whose recorded dimension differs from the denoiser.

Changing the encoder creates a new model family: released LLM2Vec Kimodo/TMR
weights are not embedding-space compatible with BGE-M3. A BGE-M3 Kimodo model
can still be evaluated with the fixed official LLM2Vec TMR evaluator for a
controlled comparison. Using BGE-M3 inside TMR itself requires retraining TMR.

## Run

Train from a published release. `--dataset-root` points at the release
directory in `DATASET_ROOT`; the skeleton and text encoder must be present in
it:

```bash
export DATASET_ROOT=/data/cms/library/releases/seed-v3

kimodo_train --config configs/train_soma.yaml \
  --dataset-root "$DATASET_ROOT" --output runs/kimodo-soma

CUDA_VISIBLE_DEVICES=0,1,2,3 torchrun --nproc_per_node=4 -m kimodo.scripts.train \
  --config configs/train_soma.yaml \
  --dataset-root "$DATASET_ROOT" --output runs/kimodo-soma
```

Training reads `skeletons/<skeleton>/{train,val}.jsonl`, `motions/`, and
`training-vectors/<encoder>/` from the release. It rejects a release published
for a different skeleton.

Before a long run, exercise the complete pipeline with the small single-device
configuration (four batch steps across both curriculum phases):

```bash
kimodo_train --config configs/train_smoke.yaml \
  --dataset-root "$DATASET_ROOT" --output runs/kimodo-smoke
```

This configuration is intentionally not architecture-compatible with released
checkpoints and its metrics are not meaningful; it validates data loading,
mmap text vectors, forward/backward, validation, EMA, logging, and checkpoint
writing.

The training loop implements 500k text-only global batch steps followed by 500k
constraint-curriculum global batch steps, 30 fps / 300 frame crops, 1000 diffusion
steps, Adam-atan2 at `2e-5`, random initial headings, and the seven weighted
Smooth-L1 terms reported in the paper. During phase two, 10% of samples remain
text-only, 25% mix two constraint families, and the sparse-keyframe limit grows
linearly from 1 to 20 while remaining biased toward fewer keyframes. Transformer
dropout changes from 0.1 to zero at the phase boundary. Text dropout is sampled
independently per item.

The final `model.safetensors` contains the EMA weights used for inference
(decay 0.995, updated every 10 batch steps). `training-state.pt` separately
stores raw weights, EMA, optimizer, mixed-precision scaler, RNG state, epoch,
micro-batch-step and global-batch-step counters for resume. One batch step
consumes `expected_global_batch_size` samples and performs one parameter update.
Single-process resume restores the exact saved RNG streams. Distributed resume
re-seeds each rank independently because the rank-zero state file does not
contain every worker's RNG stream.

## Production logging and validation

The console prints a run summary at startup and, every
`training.log_every_batch_steps`, a timestamped line with progress, phase,
loss, gradient norm, learning rate, s/step, samples/s, the share of time spent
waiting for data, GPU memory, elapsed time, and the ETA with its projected
finish time, followed by the loss components:

```text
[2026-10-22 18:00:16] step 4,000/1,000,000   0.4% P1 | loss 0.4521  gnorm 1.23  lr 2.00e-05 | 1.64s/step  312 samples/s  data 2% | mem 21.3/30.1G | 01:49:20 elapsed  ETA 18d 03:12:09 (11-09 21:12)
                      root 0.0311  heading 0.0697  joints 0.0383  vel 0.0239  rot 0.0462  contacts 0.0790  fk 0.0040
```

Loss values are means over all micro-batches since the previous line, across
all ranks. The ETA uses the rate over the last 20 log intervals (including
validation and checkpoint time) and skips the first interval, which contains
DataLoader startup. A high `data` share means the GPUs wait for the
DataLoader; raise `training.num_workers`. Validation, phase changes, and
checkpoints print their own lines.

Every rank-zero run writes `events.jsonl`, `run-metadata.json`, and an exact
`training-config.yaml` under the output directory. JSONL records training loss
components, learning rate, gradient norm, throughput, batch-step time, AMP loss
scale, phase, epoch, and CUDA allocated/reserved memory. Non-finite loss or
gradient norm terminates training immediately. A new run refuses to overwrite
an output containing `training-state.pt`; continuation requires `--resume`.

Install optional dashboards with `pip install -e ".[train]"` and select one or
more fan-out backends:

```yaml
training:
  logging:
    backends: [jsonl, tensorboard, wandb]
    project: kimodo
    run_name: soma-seed-001
    entity: null
    group: seed-retraining
    tags: [soma, seed]
```

Validation uses the release's `skeletons/<skeleton>/val.jsonl` when it
exists. For BONES-SEED this is the leakage-safe `val` split. Validation is deterministic, text-only, bounded by
`max_batches`, and evaluates EMA weights without replacing the raw training
parameters:

```yaml
training:
  validation:
    enabled: true
    every_batch_steps: 2000
    batch_size: 8
    max_batches: 32
    monitor: loss
```

`model-best.safetensors` tracks the monitored validation value;
`model.safetensors` is the final EMA model. Periodic models are written
atomically and pruned to `keep_checkpoints`, while `training-state.pt` contains
the resumable optimizer, scaler, EMA, RNG, counters, and best metric.

R@3, FID, foot skate, contact accuracy, and constraint errors require DDIM
generation over a fixed benchmark rather than a denoising validation batch.
Run the documented `benchmark/` pipeline on saved checkpoints at a lower
frequency (for example every 20k--50k steps); do not use training loss as a
replacement for those generation metrics.

`configs/train_soma.yaml` targets the report's 4-GPU global batch of 512 using
a conservative 48 GiB starting point of 16 samples per GPU. Users do not set
gradient accumulation: the trainer derives it as
`expected_global_batch_size / (batch_size * WORLD_SIZE)`. This gives 8 on four
GPUs and 32 on one GPU. The target must divide the distributed micro-batch
exactly or startup fails. Profile representative 300-frame batches before a
long run; increasing `batch_size` to 32 on four GPUs automatically reduces
accumulation to 4 while preserving the same global batch.

The Bones Rigplay data, transition-generated stitched augmentation, and
NVIDIA's exact data-mixture distribution are not public;
the manifest intentionally permits Rigplay, BONES-SEED, or a private retargeted
dataset without encoding proprietary assumptions. Consequently this entry
point is an open-data approximation of the report recipe, not a claim that the
released 700-hour checkpoint can be reproduced from BONES-SEED alone.
